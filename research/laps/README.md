# JRA公式レースラップの補助データ

JRAの結果ページからハロンタイムを取得し、`YYYYMMDD/RaceLapData.json`へ保存する。既存の23列のproduction_history、37特徴量のモデル、予測・正式シグナル・金額配分は変更しない。ペース予想にはまだ接続しない。

出典はJRA公式の結果ページ。元URL・取得時刻・元HTMLのSHA256を各レースに記録する。元HTML全体はリポジトリへ保存しない。

取得確認中に、公式の出馬表・結果リンクで `pw01dde10` / `pw01sde10` の形式が使われていることを確認した。従来の `01` 形式のみを拾う取得処理では10月12日のリンク探索に失敗したため、共通の出馬表・結果取得を `01` と `10` の両形式に対応させた。日付とレースIDを一致させる条件は維持する。

固定の開催日用URLがない場合はJRAトップページで現在の出馬表入口を見つけ、公式の公開フォームと同じPOSTで開催選択へ進む。GETではパラメータエラーになる入口を、架空のURLや推測したチェックサムで代替しない。フォームのフィールド名もページから取得する。固定シードを無効にした10月12日の実ページで、この経路を確認した。

JRA公式の定義では、ハロンタイムは各地点で先頭の馬を基準に計測する。距離が1700mなどの場合は最初に100m、その後200mごとの区間になる。

- 用語説明: https://www.jra.go.jp/kouza/yougo/w291.html
- 成績表の説明: https://www.jra.go.jp/datafile/seiseki/report/mikata4.html
- 最小テストに使う1800mの実測例: https://www.jra.go.jp/JRADB/accessS.html?CNAME=pw01sde0108202604051020261012%2FE3

URLと本文の開催日・競馬場・開催回・開催日番号・レース番号を照合する。区間数と距離、全ラップの合計と勝ち時計、最後600mと公式のレース上り3Fを照合する。馬ごとの推定上がり3Fをレースラップとして扱わない。保存済み履歴の芝ダ・距離とも一致するレースだけ収録する。

600mや1000mが計測地点にない距離では、`first600mSeconds` / `first1000mSeconds` はnullにする。補間した値を実測値として保存しない。代わりに最初の600m以降の実測地点（700mなど）と時刻、全区間の累積時刻を保持する。

既存データを再利用し、再実行では同じレースを重複保存しない。`--force`で再取得する場合も、失敗したレースの以前の有効なデータを削除しない。部分的に取得できた場合は成功分と失敗理由を残し、終了コードで失敗を知らせる。JRA開催のない日は保存済み履歴に該当レースがなければ何も変更しない。

```bash
python -m unittest discover -s production -p 'test_race_lap_runtime.py'
python -m unittest discover -s production -p 'test_jra_route_modes.py'
python production/collect_race_laps.py --date 20261012 --limit 3
python production/collect_race_laps.py --date 20261012 --apply
```

デフォルトでは本体データを書き換えず、取得確認のレポートだけを出力する。`--apply`時に研究用データへ保存する。実行前後のproduction_historyの指紋が一致することを必須とする。

21:45 JSTの専用Workflowで、履歴更新後の当日分を収集する。通常の予測公開処理と別のWorkflowなので、収集失敗でも予測を停止させない。

次の段階は2024年・2025年などのラップを遡って蓄積し、競馬場・距離・芝ダ・内外コース・馬場状態を揃えた基準を作ること。先頭候補が多いだけでハイペースと判定せず、発走前情報からの予想を別年で検証してからアプリへ接続する。
