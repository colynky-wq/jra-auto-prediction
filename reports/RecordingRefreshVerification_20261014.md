# 記録一覧の更新通信の検証

記録一覧の更新ボタン、初期取得、下へ引く再取得は同じKeibaAIRecordingStatusStore.loadを使います。端末操作の確認に先立ち、実際のSwift取得処理をXcodeで検証する仕組みを追加しました。

## 実際の処理との対応

ios/tests/build_recording_store_checks.pyはKeibaAI_NewDesignView.swiftのprivateなStore宣言だけを取り出し、Foundation・Combine・Dispatchのimportと試験プログラムを添えて一時ファイルを作ります。Storeの中身、URLSession.shared、公開URL、HTTP判定、decode、取消判定、読み込み中の制御は置換しません。境界や通信実装が変わった場合は生成を止め、試験側の確認を要求します。

試験用URLProtocolを登録し、実際のURLSession.sharedの通信をすべて試験内で応答します。公開GitHubへの取得・書き込み、本番の観測・予測は行いません。試験終了時は登録を解除します。取消が完了しない不具合は60秒の上限で試験を失敗させます。

## 確認する8群

| 条件 | 確認する動作 |
|---|---|
| 初回の正常応答 | 保存済み・保留・保存失敗を個別に読める。公開URL・キャッシュ回避・20秒の通信上限が実際のリクエストにある |
| HTTP404/500/503 | 前回の3行が残り、通信エラーを表示し、再取得できる状態に戻る |
| 空・途中で切れた・null・項目不足のJSON | 前回の一覧を置き換えず、取得失敗を表示する |
| 時間切れ・未接続・接続切断 | 前回の一覧を保ち、読み込み中が解除される |
| 失敗後の正常な再取得 | 新しい一覧へ更新し、エラーを解除する。取得URLの時刻も変わる |
| 取得中の連続更新 | 通信を1件に抑え、前回の一覧を表示したまま待ち、正常完了する |
| 取得の取消と、その後の更新 | 通信を止め、前回の一覧を保ち、取消を通信失敗として表示せず、次の取得に成功する |
| 初回取得の失敗 | dataは未取得のままで、正常な0件という応答に置き換わらない |

成功した群ごとにRECORDING_REFRESH_CASE_OK、全体の成功時にRECORDING_REFRESH_OKを出力します。GitHubのKeibaAI iOS Build and Identityへ接続し、既存の馬識別・プロフィール取得・記録DTOのSwift確認と、アプリ全体のビルドも従来どおり行います。

## 対象外の確認

この検証は実際の通信処理の確認です。端末で更新ボタンをタップしたこと、シートを閉じたこと、日付・要確認の絞り込み、画面の見た目を確認した証拠にはしません。実際の開催での新しい保存、監視状態通知、結果照合も別に確認します。

配布アプリ内のファイル、予測モデル、公開記録は変更しません。KeibaAI.zip v9も同じものを使用します。
